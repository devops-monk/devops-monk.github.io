If you run servers at home — a homelab, a NAS, a local Kubernetes cluster — you have probably hit the same wall: your ISP gives you a dynamic IP address that changes without warning. Commercial DDNS services like DynDNS or No-IP solve this, but they come with account limits, paywalls, and you surrender full control of your data. I wanted something I own end-to-end, so I built ddns.devops-monk.com — a fully self-hosted Dynamic DNS platform. This post walks through the problem, how it is architected, and how you can use or deploy it yourself.

What is Dynamic DNS?

A Dynamic DNS (DDNS) service maps a stable hostname like homelab.ddns.devops-monk.com to your current public IP address. When your ISP rotates your IP, a small client running on your machine detects the change and calls an API to update the DNS record. Anyone hitting your hostname always lands on the right IP — no manual intervention needed.

The key difference from a static DNS record is that the TTL is kept intentionally short (typically 60 seconds) so that resolvers flush their cache and pick up changes quickly when your IP rotates.

flowchart LR A["🏠 Your Home Network\n(dynamic IP)"] -->|hostname| B["homelab.ddns.devops-monk.com"] B -->|resolves to| A C["ISP rotates IP"] -->|triggers| D["DDNS Client detects change"] D -->|API call| E["DNS record updated\n(within 60 seconds)"] E --> B

DNS Delegation — The Tricky Part

This is the step most tutorials gloss over, and the part that confuses people the most. Here is the mental model:

flowchart TD REG["🏢 Porkbun Registrar\nauthoritative for devops-monk.com"] VPS["🖥️ Your VPS\nns1.devops-monk.com\nPowerDNS"] INT["🌍 Internet Resolver"]
REG -->|"NS record:\nddns → ns1.devops-monk.com"| VPS
REG -->|"A record (glue):\nns1 → VPS_IP"| VPS
INT -->|"1. Query: homelab.ddns.devops-monk.com?"| REG
REG -->|"2. Ask ns1.devops-monk.com"| INT
INT -->|"3. Query PowerDNS directly"| VPS
VPS -->|"4. Returns current A record"| INT

The four steps to set up delegation:

  1. Your registrar (e.g. Porkbun) is authoritative for devops-monk.com.
  2. Add an NS record for the ddns label pointing to your VPS: ddns NS ns1.devops-monk.com.
  3. Add an A record (the glue record) for ns1 pointing to your VPS IP.
  4. PowerDNS on the VPS becomes the sole authority for everything under ddns.devops-monk.com.

Important constraint: You cannot have both a CNAME and an NS record on the same label. If you already have a ddns CNAME pointing to your dashboard, delete it first. The NS record itself makes PowerDNS serve the apex A record (ddns.devops-monk.com → VPS IP) and all user subdomains from the same zone.

Full DNS Resolution Walk-through

When someone resolves homelab.ddns.devops-monk.com for the first time:

sequenceDiagram participant Client as DNS Client participant Root as Root Servers participant TLD as .com TLD participant Reg as Registrar NS (devops-monk.com) participant PDNS as PowerDNS (ns1.devops-monk.com)
Client->>Root: Who handles .com?
Root-->>Client: Ask the .com TLD servers
Client->>TLD: Who handles devops-monk.com?
TLD-->>Client: Ask registrar NS (Porkbun)
Client->>Reg: Who handles ddns.devops-monk.com?
Reg-->>Client: Delegated to ns1.devops-monk.com (VPS IP)
Client->>PDNS: Resolve homelab.ddns.devops-monk.com
PDNS-->>Client: A record 203.0.113.42 (TTL 60s)
Note over Client,PDNS: Cached for 60s. Next lookup goes straight to PowerDNS.

IP Update Flow

This is the heart of the system. Here is exactly what happens every time the Electron client polls:

sequenceDiagram participant EC as Electron Client participant IP as ipify.org participant API as Node.js API participant PG as PostgreSQL participant PDNS as PowerDNS participant WH as Webhook
loop Every 5 minutes
    EC->>IP: GET public IP
    IP-->>EC: 203.0.113.42
    EC->>EC: Compare with last known IP
    alt IP is unchanged
        EC->>EC: Sleep until next poll
    else IP has changed
        EC->>API: PUT /api/domains/homelab/update (Bearer TOKEN)
        API->>API: Validate Bearer token (bcrypt)
        API->>PDNS: PATCH zone - replace A record to 203.0.113.42, TTL 60
        PDNS-->>API: 204 No Content
        API->>PG: INSERT ip_history (domain_id, ip, updated_at)
        API-->>EC: ip confirmed, fqdn updated
        API->>WH: POST webhook - IP changed notification
    end
end

The 60-second TTL is a deliberate tradeoff: short enough that resolvers pick up an IP rotation within a minute, long enough that it does not hammer the authoritative server with constant queries.

PowerDNS Setup

Install PowerDNS with the MySQL backend on Ubuntu:

apt install -y pdns-server pdns-backend-mysql mysql-server

Configure the MySQL backend in /etc/powerdns/pdns.d/gmysql.conf:

launch=gmysql
gmysql-host=127.0.0.1
gmysql-user=pdns
gmysql-password=YOUR_PASSWORD
gmysql-dbname=powerdns

Enable the REST API in /etc/powerdns/pdns.conf:

api=yes
api-key=YOUR_LONG_RANDOM_KEY
webserver=yes
webserver-address=127.0.0.1
webserver-port=8081

Keep webserver-address=127.0.0.1 — only the Node.js backend on localhost needs to reach the API. Never expose port 8081 to the internet.

Create the zone and seed records in MySQL:

INSERT INTO domains (name, type) VALUES ('ddns.devops-monk.com', 'NATIVE');
SET @did = (SELECT id FROM domains WHERE name='ddns.devops-monk.com');

INSERT INTO records (domain_id, name, type, content, ttl) VALUES
  (@did, 'ddns.devops-monk.com', 'SOA',
    'ns1.devops-monk.com. hostmaster.devops-monk.com. 1 3600 600 604800 300', 300),
  (@did, 'ddns.devops-monk.com', 'NS', 'ns1.devops-monk.com', 300),
  (@did, 'ddns.devops-monk.com', 'A', 'YOUR_VPS_IP', 300);

Restart PowerDNS and verify the zone is serving:

dig @127.0.0.1 ddns.devops-monk.com SOA

The API Server

The Node.js API is written in TypeScript with Express. Authentication uses per-domain API tokens stored as bcrypt hashes in PostgreSQL — the client sends its token in the Authorization: Bearer header on every call.

The core update endpoint:

// PUT /api/domains/:subdomain/update
router.put('/:subdomain/update', authenticate, async (req, res) => {
  const ip = req.headers['x-forwarded-for'] ?? req.socket.remoteAddress;
  const fqdn = `${req.params.subdomain}.ddns.devops-monk.com.`;

  await fetch(`${PDNS_API_URL}/zones/${DDNS_ZONE}`, {
    method: 'PATCH',
    headers: { 'X-API-Key': PDNS_API_KEY, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      rrsets: [{
        name: fqdn, type: 'A', ttl: 60, changetype: 'REPLACE',
        records: [{ content: ip, disabled: false }]
      }]
    })
  });

  await db.ipHistory.create({ data: { domainId: req.domain.id, ip, updatedAt: new Date() } });
  res.json({ ip, fqdn });
});

The changetype: 'REPLACE' instruction tells PowerDNS to atomically swap the entire A rrset — no need to delete the old record first.

The Dashboard

The React dashboard at ddns.devops-monk.com gives you a full picture of all your registered domains:

  • Domain list — current IP, last-seen time, uptime percentage
  • IP history chart — Recharts area chart showing IP changes over the last hour, 3 hours, 24 hours, or 7 days, with the current IP highlighted
  • Status page — real-time health checks for the API and DNS resolution with uptime history
  • Downloads page — links to the Electron client binaries for all platforms

Dark and light themes are supported via CSS custom properties — no JavaScript overhead for theme switching.

The Electron Client

The desktop client runs as a system-tray icon. On each poll cycle it:

  1. Reads the saved API token and subdomain from local config
  2. Fetches your current public IP from https://api.ipify.org
  3. Compares it to the last known IP; if changed, calls the update endpoint
  4. Repeats every 5 minutes

One subtle Electron quirk: the default close event hides the window instead of quitting. To make Quit actually quit, the main process sets app.isQuitting = true before calling app.quit():

mainWindow.on('close', (e) => {
  if (!app.isQuitting) {
    e.preventDefault();
    mainWindow.hide();
  }
});

tray.on('right-click', () => {
  const menu = Menu.buildFromTemplate([
    { label: 'Quit', click: () => { app.isQuitting = true; app.quit(); } }
  ]);
  tray.popUpContextMenu(menu);
});

How to Use It

  1. Go to ddns.devops-monk.com and create an account.
  2. Register a subdomain (e.g. homelab). You get an API token.
  3. Download the Electron client for your OS from the Downloads page.
  4. Open the client, paste your API token and subdomain, and click Save.
  5. The client immediately updates your DNS record and keeps it current automatically.

For headless servers, skip the client and use a cron job:

*/5 * * * * curl -s -X PUT \
  -H "Authorization: Bearer YOUR_TOKEN" \
  https://ddns.devops-monk.com/api/domains/homelab/update

Self-Hosting the Platform

You need:

  • A VPS with a static IP
  • A domain where you control NS records at the registrar
  • Docker (for local dev) or Ubuntu (for production)

Quick start:

git clone https://github.com/devops-monk/home_static_ip.git
cd home_static_ip
cp .env.example .env
# Edit .env: DATABASE_URL, PDNS_API_KEY, JWT_SECRET, etc.
docker compose up -d

See the DNS setup guide and deployment guide for the full walkthrough.
