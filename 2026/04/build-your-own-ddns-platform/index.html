Build Your Own DDNS Platform: Self-Hosted Dynamic DNS with PowerDNS, Node.js, and React

DNS   DevOps   Self-hosted   Node.js   Electron

If you run servers at home — a homelab, a NAS, a local Kubernetes cluster — you have probably hit the same wall: your ISP gives you a dynamic IP address that changes without warning. Commercial DDNS services like DynDNS or No-IP solve this, but they come with account limits, paywalls, and you have no control over your data. I wanted something I own end-to-end, so I built ddns.devops-monk.com — a fully self-hosted Dynamic DNS platform. This post walks through why I built it, how it is architected, and how you can use or deploy it yourself.

What is Dynamic DNS?

A Dynamic DNS (DDNS) service maps a stable hostname like homelab.ddns.devops-monk.com to your current public IP address. When your ISP rotates your IP, a small client running on your machine detects the change and calls an API to update the DNS record. Anyone hitting your hostname always lands on the right IP — no manual intervention needed.

The difference from a static DNS record is that the TTL is kept short (typically 60 seconds) so resolvers pick up changes quickly.

Architecture Overview

The platform has four layers that talk to each other:

Your machine (Electron client)
        │  HTTPS PUT /update
        ▼
Node.js API (Express + TypeScript)
        │  PowerDNS REST API (PATCH rrsets)
        ▼
PowerDNS authoritative nameserver
        │  MySQL backend
        ▼
Internet DNS resolvers

At the top, an Electron desktop app sits in your system tray, detects public IP changes, and sends updates. The Express API validates tokens, writes A records via the PowerDNS REST API, and logs every change to a PostgreSQL database. PowerDNS serves as the authoritative nameserver for the ddns.devops-monk.com zone, backed by MySQL for record storage. Internet resolvers query PowerDNS directly once the NS delegation is in place at the registrar.

DNS Delegation — The Tricky Part

Getting the delegation right is the step most tutorials gloss over. Here is the model:

  1. Your domain registrar (e.g. Porkbun) is authoritative for devops-monk.com.
  2. You add an NS record for the ddns label pointing to your VPS: ddns NS ns1.devops-monk.com.
  3. You add an A record for ns1 pointing to the VPS IP (the glue record).
  4. PowerDNS on the VPS becomes the sole authority for everything under ddns.devops-monk.com.

One important constraint: you cannot have both a CNAME and an NS record on the same label. If you already have a ddns CNAME for the dashboard, delete it first. The NS delegation makes PowerDNS serve the apex A record (ddns.devops-monk.com → VPS IP) and all user subdomains from the same zone — no separate CNAME needed.

When someone resolves homelab.ddns.devops-monk.com:

Root servers → .com TLD → devops-monk.com registrar NS
    → "ask ns1.devops-monk.com for anything under ddns.*"
        → PowerDNS looks up MySQL → returns A record

PowerDNS Setup

Install PowerDNS with the MySQL backend on a Ubuntu VPS:

apt install -y pdns-server pdns-backend-mysql mysql-server

Configure the MySQL backend in /etc/powerdns/pdns.d/gmysql.conf:

launch=gmysql
gmysql-host=127.0.0.1
gmysql-user=pdns
gmysql-password=YOUR_PASSWORD
gmysql-dbname=powerdns

Enable the REST API in /etc/powerdns/pdns.conf:

api=yes
api-key=YOUR_LONG_RANDOM_KEY
webserver=yes
webserver-address=127.0.0.1
webserver-port=8081

Keep webserver-address=127.0.0.1 — only the Node.js backend on localhost needs to reach the API. Never expose port 8081 to the internet.

Create the zone and required records in MySQL:

INSERT INTO domains (name, type) VALUES ('ddns.devops-monk.com', 'NATIVE');
SET @did = (SELECT id FROM domains WHERE name='ddns.devops-monk.com');

INSERT INTO records (domain_id, name, type, content, ttl) VALUES
  (@did, 'ddns.devops-monk.com', 'SOA',
    'ns1.devops-monk.com. hostmaster.devops-monk.com. 1 3600 600 604800 300', 300),
  (@did, 'ddns.devops-monk.com', 'NS', 'ns1.devops-monk.com', 300),
  (@did, 'ddns.devops-monk.com', 'A', 'YOUR_VPS_IP', 300);

Restart PowerDNS to load the new zone, then verify:

dig @127.0.0.1 ddns.devops-monk.com SOA

The API Server

The Node.js API is written in TypeScript with Express. The core update endpoint:

// PUT /api/domains/:subdomain/update
router.put('/:subdomain/update', authenticate, async (req, res) => {
  const ip = req.headers['x-forwarded-for'] ?? req.socket.remoteAddress;
  const fqdn = `${req.params.subdomain}.ddns.devops-monk.com.`;

  await fetch(`${PDNS_API_URL}/zones/${DDNS_ZONE}`, {
    method: 'PATCH',
    headers: { 'X-API-Key': PDNS_API_KEY, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      rrsets: [{
        name: fqdn, type: 'A', ttl: 60, changetype: 'REPLACE',
        records: [{ content: ip, disabled: false }]
      }]
    })
  });

  await db.ipHistory.create({ data: { domainId: req.domain.id, ip, updatedAt: new Date() } });
  res.json({ ip, fqdn });
});

Authentication uses per-domain API tokens stored as bcrypt hashes in PostgreSQL. The client sends its token in the Authorization: Bearer header on every update call.

The server also sends optional webhook notifications (Discord, Slack, Telegram) whenever a domain’s IP changes — useful for monitoring.

The Dashboard

The React dashboard at ddns.devops-monk.com gives you a full picture of all your registered domains:

  • Domain list — current IP, last-seen time, uptime percentage
  • IP history chart — Recharts area chart showing IP changes over the last hour, 3 hours, 24 hours, or 7 days, with the current IP always highlighted
  • Status page — real-time health checks for the API and DNS resolution with uptime history
  • Downloads page — links to the Electron client binaries for all platforms

Dark and light themes are supported with a single toggle — CSS custom properties handle all colour switching with no JavaScript overhead.

The Electron Client

The desktop client runs as a system-tray icon. On startup it:

  1. Reads the saved API token and subdomain from local config
  2. Fetches your current public IP from https://api.ipify.org
  3. Compares it to the last known IP; if different, calls the update endpoint
  4. Repeats every 5 minutes

One subtle Electron quirk: the default close event hides the window instead of quitting. To make Quit actually quit, the main process sets app.isQuitting = true before calling app.quit():

mainWindow.on('close', (e) => {
  if (!app.isQuitting) {
    e.preventDefault();
    mainWindow.hide();
  }
});

tray.on('right-click', () => {
  const menu = Menu.buildFromTemplate([
    { label: 'Quit', click: () => { app.isQuitting = true; app.quit(); } }
  ]);
  tray.popUpContextMenu(menu);
});

Cross-Compilation

electron-builder produces native binaries for all platforms from a single macOS CI machine:

  • DDNS-Client-arm64.dmg — macOS Apple Silicon
  • DDNS-Client-x64.dmg — macOS Intel
  • ddns-client_amd64.deb — Debian/Ubuntu
  • DDNS-Client.AppImage — universal Linux
  • DDNS-Client-Setup.exe — Windows (NSIS installer)

Windows cross-compilation requires Wine on the build host (apt install wine). Binaries are served directly from Nginx at /downloads/.

How to Use It

  1. Go to ddns.devops-monk.com and create an account.
  2. Register a subdomain (e.g. homelab). You get an API token.
  3. Download the Electron client for your OS from the Downloads page.
  4. Open the client, paste your API token and subdomain, and click Save.
  5. The client immediately updates your DNS record and keeps it current automatically.

For headless servers, use a cron job instead:

*/5 * * * * curl -s -X PUT \
  -H "Authorization: Bearer YOUR_TOKEN" \
  https://ddns.devops-monk.com/api/domains/homelab/update

Self-Hosting the Platform

You need:

  • A VPS with a static IP
  • A domain where you control NS records at the registrar
  • Docker (for local dev) or Ubuntu (for production)

Quick start:

git clone https://github.com/devops-monk/home_static_ip.git
cd home_static_ip
cp .env.example .env
# Edit .env: DATABASE_URL, PDNS_API_KEY, JWT_SECRET, etc.
docker compose up -d

See DNS setup guide and deployment guide for the full walkthrough.
